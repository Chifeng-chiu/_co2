## 一、我是怎麼完成這次實驗的？（實作脈絡與方法）

在剛接觸這次作業時，我發現如果只是打開網頁版 GUI 點擊「執行」與「合成」，雖然看得到漂亮的佈局圖和彩色繞線，但很難真正搞懂背後到底發生了什麼事，也沒辦法做嚴謹的量化比較。因此，我決定用**「先視覺化觀察、再寫腳本自動化量化、最後做交叉對照與驗證」**的三階段方式來完成這次實驗：

### 1. 把自己以前寫的 HDL 推進真實的 EDA 管線
我沒有只用工具內建的範例，而是翻出自己之前在 `nand2tetris` 親手寫的 Project 1、2、3、5（包含 `And`、`Inc16`、`ALU` 到最複雜的 `CPU`），一字不改地直接餵給 `hack-computer` 的模擬器與迷你 EDA 引擎。看著自己當初湊出來的邏輯閘，一步步被拆解成底層 `NAND/DFF`、再變成 FPGA 的 `LUT4` 網格與 ASIC 的標準元件列（Standard Cell Rows），讓我第一次把「計算機結構的資料流」跟「實體晶片的面積與繞線」連結起來。

### 2. 不只看 GUI，自己寫 Node.js 腳本把數據「撈」出來
因為網頁介面每次只能看一個畫面，而且**模擬退火（Simulated Annealing, SA）佈局具有隨機性**，看單次結果並不準確。為了解決這個問題，我直接呼叫 `hack-computer` 底層的 `lib/fpga` 與 `lib/asic` 函式庫，自己寫了兩支自動化腳本（放在 `data/` 資料夾）：
- **`report_flow.mjs`（自動化合成與統計）**：自動跑完 ① RTL 展開 → ② 網表 → ③ 最佳化 → ④ 技術映射 → ⑤ 佈局 → ⑥ 繞線 → ⑦ 靜態時序分析（STA），並且針對 FPGA 模擬退火**連續跑 5 次取中位數**，排除隨機誤差，輸出成結構化的 JSON 數據。
- **`verify_equiv.mjs`（20,000 組隨機向量等效性驗證）**：為了證明「EDA 工具把我的電路最佳化、拆成 LUT 或標準元件後，功能真的沒有壞掉」，我寫了這支驗證腳本，把 DFF 狀態切開當作自由輸入，對每個電路灌入 **20,000 組隨機測試向量**，同時比對「原始展平 NAND 網表」、「FPGA LUT4 網表」與「ASIC 標準元件網表」的每一個輸出位元，最終驗證 **0 錯誤（完全等價）**。

### 3. 設計「我的寫法 vs 官方標準解答」的對照實驗
我很好奇：「如果兩個人的 HDL 功能一模一樣，但寫法有一點點不同，EDA 合成出來的晶片會一樣嗎？」因此我把工具內建的官方標準解答（Builtin Corpus）當作對照組，跟我的設計跑完全相同的流程。這個決定讓我觀察到了這次實驗最有趣的現象（詳見下方心得）。

### 4. 用第二套工具（`veryl2chip IDE`）與 Cornell ECE 5745 講義做交叉印證
為了確認 `hack-computer` 的流程不是特例，我同時操作了基於 Rust + WebAssembly 的 `veryl2chip IDE`，並對照 Cornell ECE 5745 的合成與實體設計演算法講義，確認從 GTECH 展開、AIG 化簡、技術映射到 SA 佈局與迷宮繞線，確實是貫穿教育界與工業界 EDA 的共通核心架構。

## 二、實驗後，我對 IC EDA 的新理解與看法

以前學數位邏輯或寫 HDL 時，總覺得「合成（Synthesis）」就像一個魔法黑盒子——按個按鈕，程式碼就會自動變成最完美的硬體電路。但親手拆解並跑完這次的 EDA 流程後，我對 IC 設計有了五個截然不同的新體悟：

### 1. 「寫程式碼」跟「設計硬體」思維完全不同：寫法的一點小差異，會被啟發式演算法放大
這次實驗最讓我驚訝的發現，是我寫的 `ALU.hdl` 與官方解答明明功能 100% 相同，展平後的原始 NAND 閘數也只差 1 顆（1,279 vs 1,278），但經過 FPGA 技術映射後，**我的版本用了 209 顆 LUT4，官方卻只用了 177 顆（差了 18.1%）！** 相反地，切到 ASIC 後端時，我的面積（1,027 µm²）卻又比官方（1,175 µm²）小了 13%，速度還更快。
- **我的新理解**：以前以為只要邏輯等價，合成器就會幫我們化簡成同一個電路；現在才明白，因為技術映射（Tech Mapping）與佈局都是 **NP-hard 問題**，EDA 工具必須依賴**貪婪（Greedy）或啟發式（Heuristic）演算法**。只要 HDL 裡訊號宣告的順序或別名不同，展開後 DAG（有向無環圖）的走訪順序就會改變，導致「先覆蓋哪個邏輯錐」出現分歧。這讓我深刻體會到為什麼真實 IC 設計工程師這麼講究 RTL Coding Style，甚至需要下 `keep` 或 `dont_touch` 等約束（Constraints）來引導 EDA 工具。

### 2. 面積小 ≠ 速度快：決定晶片頻率的是「邏輯深度（Critical Path）」而非總閘數
在測 `Inc16`（16 位元遞增器）時，我的版本映射出 44 顆 LUT4，Fmax 高達 **46.0 MHz**；對照組雖然在最佳化階段砍掉了 41.7% 的 NAND 閘，映射出 60 顆 LUT4，但 Fmax 卻只有 **23.0 MHz**（慢了一倍）。而在 `ALU` 中，30.45 ns 的關鍵路徑換算下來約為 25 級 LUT，幾乎全卡在 `Add16` 的 16 位元漣波進位鏈（Ripple-Carry Chain）上。
- **我的新理解**：以前總覺得閘數越少、電路就越快；做完 STA（靜態時序分析）並看著紅色的關鍵路徑（Critical Path）亮起來時，我才真正看懂——**決定最高時脈 $F_{\max}$ 的永遠是最慢、最深的那一條路徑**。就算把旁支的邏輯面積縮到再小，只要進位鏈的「級數深度」沒變，晶片就跑不快。這也讓我瞬間理解為什麼計算機結構課本要花那麼多篇幅講超前進位加法器（Carry-Lookahead Adder, CLA）與管線化（Pipelining）。

### 3. 親眼看見 FPGA 與 ASIC 的本質取捨：「用面積換彈性」vs「極致客製化」
在同一個 `CPU` 電路下，切換 FPGA 與 ASIC 視圖給了我極強的視覺衝擊：
- **FPGA** 把一堆複雜的組合邏輯直接塞進 372 顆 LUT4 裡（靠 16-bit 真值表查表搞定），元件數量看起來很少，但每過一級 LUT 就要付 **1.2 ns** 的固定過路費（Fmax 26.1 MHz）。
- **ASIC** 則必須老老實實用 1,205 顆 `INV`、`NAND2`、`AOI21`、`MUX2` 標準元件把邏輯硬兜出來，雖然元件數暴增，但單級延遲只有 **0.08～0.20 ns**，讓 Fmax 直接衝上 **45.1 MHz（快了 73%，ALU 甚至快了 105%）**。
- **我的新理解**：這讓我具體看懂了什麼叫做「FPGA 用面積與速度換取重編程的彈性，而 ASIC 用高額 NRE（光罩成本）與複雜實體設計換取極致的 PPA（功耗、效能、面積）」。

### 4. EDA 不是魔法，而是由一層層經典演算法堆疊出來的工程結晶
以前聽到「邏輯合成」、「自動佈局繞線（APR）」覺得深不可測，但透過這次的開源工具把每一層拆開來看，我發現它們其實就是我們在資工系學到的演算法的具體應用：
- **展開與最佳化**：就是編譯器原理的 AST 解析、DAG 圖論化簡、常數折疊（Constant Propagation）與迪摩根定律代數消去。
- **自動佈局（Placement）**：就是用**模擬退火法（Simulated Annealing）**在溫度冷卻過程中不斷隨機交換格子，去最小化 **HPWL（半週長線長）** 成本函數（看著 CPU 的 HPWL 從 2678 一路降到 1110 超級療癒）。
- **自動繞線（Routing）與時序分析（STA）**：就是圖論裡的 **A* 迷宮搜尋演算法**（避開壅塞通道）與 **DAG 最長路徑搜尋（Topological Sort + Dynamic Programming）**。
這讓我對資工系學的資料結構與演算法有了全新的敬意——原來晶片設計自動化的底層，全都是軟體演算法在撐腰！

### 5. 看懂「教學模型」與「真實工業界 Tape-out」的距離
雖然這兩套開源工具讓我走完了 ①～⑦ 的完整流程，但在實驗過程中我也清楚意識到模型的簡化之處：例如當我嘗試合成包含 `RAM16K` 與 `Screen` 的電腦時，工具會報錯不支援黑盒子記憶體（在真實 ASIC 中，這需要呼叫 Memory Compiler 產生 SRAM Macro 並進行 Floorplanning）；此外，本實驗的時序模型採用固定線延遲估計，且退火只看 HPWL，因此繞線變短對 Fmax 影響不大。但在真實奈米製程（或如 `veryl2chip` 支援的 SKY130 PDK 與 OpenLANE 流程）中，還必須面對**時脈樹合成（CTS）、Setup/Hold Slack 修補、寄生電容萃取（RC Extraction）、繞線壅塞（Congestion）與時序驅動佈局（Timing-Driven Placement）**。認識到「工具做得到什麼、簡化了什麼」，是我這次實驗除了數據之外最大的收穫。
